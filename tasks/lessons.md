2026-06-24 | RuleEditor on-screen back arrow did nothing (system back worked). 2026-06-24 | A `| tail -40` pipe on `./gradlew` reported the pipeline exit as 0 even though gradle printed "BUILD FAILED" (tail succeeded), nearly masking a real failure. | To capture a gradle build's REAL status, redirect to a log and read `$?` of gradle itself (`./gradlew ... > log 2>&1; echo "EXIT=$?"`), not the exit of a piped `tail`/`grep`.

2026-06-24 | Premium-motion diff shipped `Modifier.cascadeItem(index)` at 4 call sites, but `cascadeItem` is declared `fun LazyItemScope.cascadeItem(...)` — so it was being called on the `Modifier` companion (not a `LazyItemScope`) and failed `:app:compileDebugKotlin` with "receiver type mismatch". `Modifier.riseIn(...)` was fine because `riseIn` extends `Modifier`. | A motion helper's extension RECEIVER dictates the call form: `LazyItemScope` helpers (cascadeItem/animatedItem) must be called BARE inside `itemsIndexed { i, x -> ... }` (resolving the implicit scope receiver) and passed as `modifier = cascadeItem(i)`; `Modifier` helpers (riseIn/pressElevation/sheen) are called as `Modifier.x()`. Never reflexively prefix `Modifier.` — check whether the receiver is LazyItemScope or Modifier first, and always run the compile.

2026-06-24 | Verifying "no de.robv Xposed classes bundled" via `unzip -l app-debug.apk | grep de/robv` returned 0 — but that 0 was MEANINGLESS: Kotlin/Java classes compile into `classes*.dex`, never listed as individual zip entries, so unzip -l can't see ANY app class (de.robv OR com.quietping). | To check what an APK actually bundles, inspect the DEX not the zip listing. Extract `classes*.dex`, then `strings *.dex | grep -oE "L<pkg>/..."` shows REFERENCES, and `dexdump -f` + grep "Class descriptor .*L<pkg>" shows DEFINITIONS. For a `compileOnly` dep, expect type references (your code calls them) but ZERO defined classes — references are correct/required, definitions are the leak. dexdump: `~/Library/Android/sdk/build-tools/<v>/dexdump`.
2026-06-24 | Xposed `AndroidAppHelper` (used to get the host `Application`/Context from inside a hooked process) was imported as `de.robv.android.xposed.AndroidAppHelper` → "Unresolved reference". | `AndroidAppHelper` lives in package `android.app` (a hidden framework class the Xposed API jar exposes), NOT `de.robv.android.xposed`. Import `android.app.AndroidAppHelper`. Most Xposed types ARE under `de.robv.android.xposed.*` (XposedBridge, XposedHelpers, XSharedPreferences, IXposedHookLoadPackage, callbacks.XC_LoadPackage) — AndroidAppHelper is the exception.
2026-06-24 | Cross-UID IPC auth (Face 2 hook inside WhatsApp → Face 1 vault) was first built as an exported BroadcastReceiver + a shared token stored in the world-readable gate prefs. Security review (HIGH): the token file is world-readable (REQUIRED so the hook can read it), so ANY app reads the token and spoofs a delivery → fake vault injection. A secret in world-readable storage is not an auth boundary. | For cross-UID delivery, authenticate by KERNEL-ENFORCED caller UID, not a shared secret. BroadcastReceiver.onReceive does NOT expose the sender UID — use a primitive that does: ContentProvider.call() (or a bound Service) where Binder.getCallingUid() is reliable, then PackageManager.getPackagesForUid() must resolve to an allowlisted package. Hilt can't inject a ContentProvider (it inits before the Hilt component) — fetch singletons inside call() via EntryPointAccessors.fromApplication(). Signature-perm auth fails here because the legit sender runs as the TARGET app's UID, not QuietPing's signature.

A green `:app:testDebugUnitTest` after an interface change is the only proof the fakes kept up; re-run it after each external-modification system-reminder, since concurrent edits arrive in waves.
